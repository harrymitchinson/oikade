# Architecture

How Oikade works inside, as it is now. It's for anyone changing the code. What a user writes and sees is in the [README](../README.md), and the plugin protocol is in [plugin-contract.md](plugin-contract.md).

This page says how things work, not why they were chosen. Each section links the Linear issue that holds the design and its discussion. When a change makes a section wrong, the same PR fixes it.

## Who owns what

| Owner | Holds |
|---|---|
| Git, as a Go module | Your automations: holds, moments, flows, arbitration settings, and a copy of the device list (`oikade types`) |
| The host's data directory | Devices, names, rooms and endpoints (the registry), claims, latches, flows' journals, deployed versions, Matter's identity and fabrics, secrets |
| Apps | Their own names. Drivers find a device by its ID, never by its name in the app, and the host copies a name once ([OIK-130](https://linear.app/oikade/issue/OIK-130)) |
| Prometheus, Grafana and Loki | Values over time, changes and rule runs |

## Components

There are two binaries ([OIK-170](https://linear.app/oikade/issue/OIK-170)). `oikade-host` (`cmd/oikade-host`) is the host, and `oikade` (`cmd/oikade`) is every command you run, which reach the host over its API. `oikade` links neither `internal/host` nor Matter, and `test/cli` checks that it stays so. What both share as commands, such as reading flags and the version, is `internal/cli`. [The host](#the-host) is one process per home, with your process and each plugin as children it supervises. There's no second host, because two would run every rule twice. Anything that assumes it's highly available, or needs leader election, is a design decision.

### The data path

```
driver ──▶ hub ──▶ metrics, event log, your process, Matter bridge
  ▲
  └── Set ◀── arbitration ◀── your process, Matter bridge, oikade set
```

- **A driver** translates one integration to capabilities. It reports to a `driver.Sink` (`Discovered`, `Changed`, `Availability`, `Seen`, `Undeclared`, and `Inventory`: every device it sees in its app, declared or not) and takes writes as a `driver.Setter`. The drivers are `plugins/zigbee2mqtt` and `internal/driver/plugin`. A new kind of integration is usually a plugin.
- **The hub** (`internal/hub`) holds the latest state of each device and fans updates out.
- **Capabilities** (`internal/capability`) are the protocol-neutral names and value types every consumer uses. Drivers convert to them, and nothing after the driver knows about vendor payloads.

### Drivers

- **Zigbee2MQTT.** `plugins/zigbee2mqtt` is a plugin a home imports. It maps each device's exposes to capabilities. It connects to a Zigbee2MQTT and a broker you run, and the host starts neither ([OIK-155](https://linear.app/oikade/issue/OIK-155)). It reports every paired device by IEEE address, with `ReportState`. After each device list it sends a paced `/get` for each property that an expose's `access` says can be read and that has no value yet, retained or reported, on a device Zigbee2MQTT doesn't say is offline ([OIK-53](https://linear.app/oikade/issue/OIK-53)). A sleeping sensor can't be asked, so it relies on `retain`. It treats `<base>/bridge/state`, which is Zigbee2MQTT's Last Will, and its own broker connection as the health of Zigbee2MQTT: either going offline marks its devices offline and refuses writes.
- **Plugins** speak the [oikade/v1 contract](plugin-contract.md) under `oikade/v1/<namespace>/<plugin>/`. The driver validates every message against the contract and the capability registry, and drops and counts what doesn't fit. The Go SDK is `sdk/plugin`, and the contract types are `contract/v1`. First-party plugins live in `plugins/`, and anyone else's in its own repo, which checks itself with the `oikade-conformance` command (`cmd/oikade-conformance`, wrapping `internal/conformance`), as [plugin-contract.md](plugin-contract.md#conformance) describes. Here, `make test-conformance` drives the simulated-relay fixture `test/fixtures/simswitch` through it, so an SDK change is tested end to end in its own PR. Design: [OIK-61](https://linear.app/oikade/issue/OIK-61) (plugin drivers) and [OIK-62](https://linear.app/oikade/issue/OIK-62) (the Go SDK).

## The host

`oikade-host` (`cmd/oikade-host`, `internal/host`) is how Oikade runs ([OIK-143](https://linear.app/oikade/issue/OIK-143)).

```
                 host (long-lived)                         your process (replaceable)
┌──────────────────────────────────────────┐          ┌───────────────────────────────┐
│ device state (hub.Store)                 │─changes─▶│ mirror of device state        │
│ arbitration (an engine with no rules)    │◀─claims──│ triggers, conditions, holds   │
│ device writes                            │◀─writes──│ (an engine with no arbiters)  │
│ the store: hold state, latches, claims,  │◀─saves───│                               │
│ the journal                              │─ping────▶│                               │
│ supervision, your binaries               │◀─pong────│                               │
│ the Matter bridge                        │          │                               │
└──────────────────────────────────────────┘          └───────────────────────────────┘
```

- **The split.** Both sides run the real `internal/engine`. The host's has no rules, so it only runs arbiters and their timers, and owns the store. Yours has every rule and no arbiters: `engine.Arbitration` sends its claims to the host, `engine.States` saves hold state there, and writes go through `driver.Setter`.
- **Your process** is your binary, built from `framework`, a public package. A home's `main` declares holds, moments and flows and calls `framework.Run`. Its exported API can't mention `internal/`: `internal/apicheck` fails a test if it does.
- **The mirror.** Conditions read a copy of the device state held in your process, so they never wait for a socket. So do hold states, read once from the `welcome`: the engine reads them with its lock held. Everything that changes the host's state is a request that waits for its answer, and none is sent with the lock held.
- **Surviving a kill.** Device state, claims and latches are in the host, so killing your process loses none of them. The next process gets the saved hold states and works each hold out again, and writes only if the hold started or ended meanwhile. A write and the save after it aren't atomic: a process killed between the two repeats the write, unless the capability is arbitrated, where a repeat claim changes nothing.
- **Supervision.** The host starts your process, restarts it with backoff, and kills one that stops answering. A condition stuck in a loop stops the answers. Exactly one process runs at a time, and the host refuses any other. [host-protocol.md](host-protocol.md) has the details, and says what happens to a process's claims.
- **Claims outlive a crash of the host.** Saving arbiters' state is a background job. The host's answer to a claim or a release is a promise, so it saves first (`Engine.flushControls`). An arbiter's other changes, such as a write it has made, still save in the background.
- **Durable flows** (`internal/flow`). A flow is ordinary Go, and [writing-flows.md](writing-flows.md) is how to write one. Each step sends a journal entry, the host writes it to the store, and only then does the flow continue. A step's effect comes first and its entry second, so a crash between the two repeats the effect: actions run at least once. After a crash the `welcome` returns every unfinished run, and the flow reruns from the top with recorded steps returning their recorded results. The first step that isn't recorded is where it carries on.
- **What can't resume.** An entry records a step's kind and arguments, so a replay notices code that takes different steps, and drops the run and logs it. A run past its latest useful time gives up, and logs that, unless it's a Safety flow. A run's ID is never reused, since the journal numbers a run from 1. Only the newest run of a flow resumes, and `internal/flow` stops a run by panicking through the flow, because a step has no error to return for these.
- **Times of day.** Sunrise and sunset are worked out in your process by `internal/sun`, for the `Home.Site` that `framework` gives `Engine.Site`. `simhome` takes the same `Site`, so `oikade dev`, `oikade replay` and `hometest` agree with the house. The host's engine only arbitrates, and has none. `Compiled.Since` comes from the host, which saves when each rule's timers were last accounted for. So a time missed while no process ran fires when one starts, within the same limit as a late flow, and a save lost to a crash means catching up once more.
- **Deploys.** The host keeps your binaries in the data directory, and the store says which is running. `oikade deploy` checks your flows and builds your module for the host's platform, and the host checks the result before anything stops. It stops the old process, starts the new one and watches it settle, and a failure brings the last one back. [host-protocol.md](host-protocol.md#deploys) has the order. `--home` only says what to run until the first deploy.
- **The API** (`internal/host/api`, [`docs/host-api.md`](host-api.md)). HTTP on `api.sock`, one connection a call, with newline-delimited JSON for `tail`, which `internal/host/feed.go` fans out without ever waiting for a reader. It's apart from `host.sock`, which only your process uses, and both are `0600`. A `Transport` reaches it: `Local` dials the socket, which needs no authentication of its own, and `Remote` dials the network API with a pinned key and a token. `--api-addr` serves the same routes over TLS (`internal/host/apiauth.go`), with a self-signed key in the store's `api` namespace and a bearer token for each client, kept as its SHA-256.
- **The device registry** (`internal/registry`). The store holds it as one value, so a device and the endpoint counter can't disagree after a crash, and an unreadable one stops the host rather than starting empty and handing out endpoints again. `internal/host/devices.go` keeps the live state in `hub.Store` in step, by giving each driver instance the registry's devices: the hub's key is the registry's name, and a driver finds that from its hardware's ID. An endpoint belongs to one registry entry for good: `Next` only rises, including through a restore, removed devices stay on record, and a name moved onto new hardware keeps its entry's endpoint and retires the replacement's. Claims are keyed by name, so renaming a claimed device is refused, as is a restore that would move a claimed name, and removing a device ends its claims (`Engine.ForgetDevice`) rather than leaving them for the next device of that name. Claims a device has only on disk count too (`Engine.SavedClaims`). A record that can't be read counts as a Safety claim on the whole device (`Engine.UnreadableClaim`): it stays, no arbiter starts empty to save over it, `claimedSetter` refuses every write to the device, and removing the device with `--allow-safety` clears it. A device's arbitration settings are on record with it, so a host loads its arbiters as soon as a driver instance attaches, and a claim holds before the device reports. A home's `Control` arrives in the process's Hello, and overlays them by capability. It's saved first, in its own namespace, so a host that restarts arbitrates what the last code said before any process attaches. A process only adds and changes settings (`inventory.takeHome`), and a process turned away has no say. Dropping one ends its claims, so that waits for the version to settle (`deployer.removals`), and a deploy that would end a Safety claim that way is refused without `--allow-safety-removal`. They stay with a name on a `replace`. Running code still has a device's old name until a deploy, so changing one needs `--allow-safety` while a Safety rule runs. `oikade types` renders the registry to Go (`internal/registry/types.go`): a value per device, with its name and a `framework.Handle` for each capability it has, named by the capability registry's `Go` name, so the compiler checks what a home names. Comment lines of JSON follow, which `oikade devices restore` parses. It refuses a file that disagrees with a registry in use, unless forced. Your process isn't told a device went: it's told about new and changed ones, and a deploy gives it a fresh list. A device stays until you remove it.
- **Plugins** (`internal/host/plugins.go`). Each plugin your binary imports runs as `<binary> plugin <name>`, with the same supervision and heartbeat as your automations (`Host.watch`) and its own backoff. The host learns their names from check mode, and only a change of binary restarts them, so a deploy does and a crash of your automations doesn't. The SDK's `Plugin` publishes through a `link`, a broker or the host's socket, so a `Handler` is the same on both. A plugin process speaks `internal/host/pluginwire`, the part of the protocol with no engine types, so the SDK doesn't link the engine. `socketBus` makes a session look like an `mqtt.Bus`, so `internal/driver/plugin` decodes imported and outside plugins alike, and there's one set of checks. A plugin outlives its processes in the host: its decoder stays, and it keeps a process's devices known while none runs. Every plugin on record attaches at start, so a claim on its devices is enforced before any process connects, and `routedSetter` sends each write to the device's driver, for your code, `oikade set` and Matter alike. After a `devices` report the host records what it hears in the registry, and tells the decoder which device each ID is, which is why a plugin needs no list of devices. `Engine.RuleClaims` and `EndRule` also see claims that are only on disk, for a device whose driver is yet to attach, so a deploy check can't miss one.
- **Matter** (`internal/host/matter.go`). The node runs in the host with no bus between them, so controllers don't notice your process. `matterBridge` wraps `matterbridge.Bridge`, which is a `driver.Sink` of the hub, and calls its `Apply` with what the registry says whenever the registry or a device's discovery changes. A bridged device's `UniqueID` comes from the bridge's unique ID and the endpoint, because the endpoint is what follows a device through a rename or a replacement. Only reserved and removed devices stay off. The store's `matter` namespace holds the `identity`, written once before a controller can see it, and the `fabrics`. `fabric.Table` saves through `fabric.Store`, so a fabric is on disk before commissioning hears it worked. Unreadable Matter state leaves the bridge broken for good, with no node and nothing retried, and the home running: a new identity would lose every controller silently, and `oikade matter` and the log say why. A bridge that can't start or stops serving, as with a taken port, tries again every `matterRetry`, and `node.Run` can run again after it returns. A controller's write goes through `matterWrites`: it refuses against a Safety claim, on disk or in an arbiter, then records the write, so the device's change counts as `Matter`.
- **Pauses.** The store holds them, and the host tells your process in the `welcome`, then with `pause` and `resume` messages. The process keeps a paused rule out of its engine. The host ends the rule's claims as well, since no process may be running to do it.
- **Metrics.** Host and device metrics come from the host. Rules run in your process, which sends its metrics in Prometheus's text format every 5 seconds, so Prometheus scrapes one target that outlives deploys. `internal/host/observe.go` merges them. The Matter bridge's come from an `im.Observer` the node hands to its Interaction Model server, and from the node's fabrics, sessions and subscriptions, read at each scrape (`internal/host/matter_metrics.go`). Their labels are a cluster's name and a status, never a node ID, which a controller chooses. The HTTP listener only reads.
- **Fault points.** `internal/fault` marks where a crash matters, and compiles to nothing unless built with the `faultpoints` tag, which only `test/host` uses. `TestKilledAtEveryJournalBoundary` uses them to kill each side at every journal write, just before and just after it's durable. `TestBrokenWriteAheadFailsTheCheck` proves that test can fail.
- **Secrets** (`internal/host/secrets.go`). A directory with one file each. The host passes on the directory as `OIKADE_SECRETS_DIR`, never a value, so nothing reads one but the code it's for. `oikade secret set` is the one call that carries a value, and it's in no log or answer. A read-only directory means they're managed elsewhere. `mqtt.Connect` doesn't quote its URL in errors, and the host's logs use `redacted`, since a URL can carry a password.

## Rules

The engine (`internal/engine`) runs what `framework` compiles from your home, in your process. Design: [OIK-64](https://linear.app/oikade/issue/OIK-64) (the rule model) and [OIK-60](https://linear.app/oikade/issue/OIK-60) (room targets).

- **Moments** run their actions when a trigger fires and the condition holds. Times of day are timers. A room target resolves to its members when the trigger or action runs, not when the rule loads, so a device added to a room is covered at once.
- **Holds** aren't timed in memory. The engine works out from the clock and the devices' state whether each hold is active, and when that next changes. It saves each hold's state, so after a restart it writes only if the hold started or ended while it was down.
- **A report is applied as a whole** ([OIK-212](https://linear.app/oikade/issue/OIK-212)). A driver passes every value one report from a device changed to `driver.Sink.Changed` in one call, the store takes them all in before its listeners hear, the host sends them to your process as one `change`, and the engine handles them as one event. So every hold looks at the whole report. The writes the holds start in one look, a report or a timer, then run in order (`Engine.startWrites`). Claims go highest level first: a Safety claim is in before a Normal one from the same report, so the arbiter never writes the Normal value, even for a moment. Plain writes, with no `Control` to arbitrate them, go lowest level first, so the highest level's value is the one that stays. Only writes that can reach the same device, in one room or to one device with no room, wait for each other. A moment the same look sets off starts once those writes are in. `oikade replay` puts a device's changes at the same moment back into one report.
- **Arbitration** (`internal/control`) decides an arbitrated capability. Rules, Matter controllers and the device itself make claims at a level (Safety, Override, Normal). The highest level wins, the Device's `resolve` breaks ties within a level, and then the equipment limits hold the winner back. A controller's write reaches the engine in the host, so it becomes a `Matter` claim.
- **Rules in Go** (`internal/engine/rule.go`). `NewMoment`, `NewHold`, `NewFlow` and `NewTrigger` build the engine's input, which `framework` calls for [the host](#the-host). A condition runs with the engine's lock held, so it must not block. Its `Vars` carry each device's values and its room and device types (`hub.Member`), so a condition can read a room ([OIK-180](https://linear.app/oikade/issue/OIK-180)). A hold with a condition looks again on any change to a device, and when a device is announced again, as a move to another room or a new device type announces it.
- **The day planner** (`internal/schedule`) lays out a day in 15-minute slots that rules require, forbid or prefer, and spends a daily budget across them. A budget is a `schedule.Spec`, and its plan lives in `HoldState.Budget`, so it survives a deploy.

### Simulated homes

`internal/simhome` runs a home in one process: one `Engine` with both rules and arbiters on a fake clock, with its states and journal in memory. `oikade dev` is your binary's `dev` role reading commands from standard input, and `framework/hometest` is the same thing in a test. `framework` fills in `simhome.FromFramework` when it loads, because a public package can't name a home's compiled form. `Sim.settle` needs to know the engine has caught up, and `Engine.Idle` says so exactly: the engine counts what it has in flight (changes queued, a wake or save asked for, every goroutine it starts), and a run stops counting while it waits through `Engine.Park`, as the engine's own waits and a flow's do. A parked run whose time has come, or whose change has happened, isn't waiting any more, a run cancelled mid-wait is busy until it ends, a failed save is owed until one succeeds, and the engine knows when its own timer is due. `Engine.ParkedUntil` says when the next parked run wakes, so `Advance` can move straight to the next wake-up. A restart builds a new engine from the states and journal, as a new process would, so `flow.Recover` runs for real.

`oikade replay` is a `Sim` too (`internal/simhome/replay.go`). The command builds your module and hands its binary a file with the host's event log, and the binary runs the log through a `Sim` and prints a report, so the host never runs your working copy. Changes within 10 seconds of a write to the same capability are the device answering it, and don't go in: otherwise the deployed version's writes would happen whatever your code does. A device's first value starts it off, rather than going in as a change. Flows' outside calls don't run: `Flow.Dry` answers each from the log, by name and in order.

### Embedded store

`internal/store` is [the host's](#the-host) state store.

- One data directory holds one [bbolt](https://github.com/etcd-io/bbolt) file, `oikade.db`, and only one process can have it open. The operating system drops that lock when the process dies, so a crash never leaves it locked. A second process gets a clear error.
- Namespaces share the file with separate keys, for the registry, latches, claims and Matter state. `engine.Stored` implements `engine.States` on a namespace.
- The journal keeps ordered entries per run. `Append` returns only once its entry is on disk. Each write is one transaction with two fsyncs, so its cost is about twice the disk's fsync time. A crash mid-write loses only the entry that was never acknowledged.
- The file records its format version, and `Open` refuses one it doesn't know.

The event log (`store.Events`, fed by `internal/host/eventlog.go`) lives here too, as what `oikade replay` reads. It's history, not state: nothing depends on it, so it trades the rest of the store's durability for staying out of the way. Reporting an event only appends to a queue. One commit every 5 seconds takes the queue, so a crash loses at most that long, and past 4096 waiting events new ones are dropped, not waited for. That commit also drops the oldest events over the bound, folding their last values into a baseline in the same transaction, because a device that hasn't changed since still has them. A reader takes the log in pages, each its own short transaction: a long one would hold up writes that grow the file, journal entries among them.

The default bound is 14 days or 64 MiB, whichever comes first. It's sized on an estimated home of 50 devices at about 24,000 events a day, which holds 14 days in about 31 MiB and a 48 MiB file, so the size bound has room for a home twice as busy. That estimate is in `internal/host/eventlog_test.go`, and no real home has measured it yet. With a full 64 MiB log and a commit every 20 ms, the journal's median append went from 9.0 to 10.0 ms on a Mac's SSD (`TestAFullLogDoesntSlowTheJournal`).

## Matter

Oikade reaches the Home app and other controllers as a Matter bridge. It replaced a HomeKit bridge built on an unmaintained library ([OIK-76](https://linear.app/oikade/issue/OIK-76)). The Matter stack is Oikade's own, in `internal/matter`, built from the Matter Core Specification: TLV, the message layer with MRP over UDP, PASE and CASE, operational certificates, the Interaction Model, the commissioning clusters, attestation with connectedhomeip's test DAC, and an mDNS responder. `internal/matter/node` wires them into a node serving a bridge, and [the host](#the-host) runs one.

- **The mapping** (`internal/matterbridge`) makes each device on record with an endpoint ID one bridged endpoint, with a device type per function and their clusters, and Power Source for a battery. What a device that's on or off is comes from `internal/devicetype`, the one answer `oikade devices` reads too: the registry's `deviceType`, set by `oikade devices type`, else its `driverDeviceType`, from the driver's report, else a dimmable light with `brightness` and a plug-in unit without ([OIK-142](https://linear.app/oikade/issue/OIK-142)). Level Control comes with a dimmable type, not with `brightness` alone. A device whose capabilities or device type change is rebuilt on the same endpoint ID. A new name isn't a rebuild: it sets the Bridged Device Basic Information's NodeLabel in place, and subscribers are sent it ([OIK-130](https://linear.app/oikade/issue/OIK-130)). State reaches attributes under the node's lock, and availability is the Bridged Device Basic Information's Reachable.
- **Writes** from controllers go through a coalescer: per device and capability the last command in a 50 ms window wins, and one that matches the device's state is dropped. A device's bursts are sent one at a time, in order, so a slow device can't take an older command after a newer one.
- **Commissioning** (`internal/matter/clusters`) owns every commissioning window, including the initial one the node opens while it's on no fabric, which closes after 15 minutes, on RevokeCommissioning, or once commissioned. The node advertises each fabric's operational service when AddNOC or UpdateNOC changes it, and again when the fail-safe rolls it back. Ending a session sends CloseSession, and a peer's CloseSession ends its session.
- **Panics** (`internal/matter/contain`). Matter parses whatever anyone on the network sends, so a bug there costs the message and its session, not the home ([OIK-172](https://linear.app/oikade/issue/OIK-172)). It's the one place the host recovers from a panic, and only for work whose state goes with it: the transport's read of each packet, each handler on its exchange, each subscription's reports, and the mDNS responder's answer to a packet. Each defers `contain.Recover` itself, since a recover covers only its own goroutine. A panic ends the session it came on as the node always does, with CloseSession on a secure one, so the controller starts again, and a handshake that panics takes out the secure session it had added. The locks those paths take go with `defer`, the Node's included, and what an Update changed before a panic is still announced, so a contained panic can't leave a lock held and turn a crash into a hang. Some state can't be left half moved: the commissioning clusters' commands and writes defer `contain.Critical`, which `Recover` passes on, and timers and commissioning hooks aren't contained, so a panic there stops the host, which starts again clean. Each contained panic is logged with its stack and counted through the node's `im.Observer` in `oikade_matter_panics_total`.

## Releases

release-please keeps a release PR open on main. Merging it tags the release, and `.github/workflows/release.yml` runs GoReleaser (`.goreleaser.yaml`) on the tag: it builds `oikade` for darwin and linux and `oikade-host` for linux, on arm64 and amd64, attaches them as `.tar.gz` archives with checksums to the Release release-please made, keeping its notes, and pushes the image. The Dockerfile copies the prebuilt `oikade-host` rather than compiling it, so the image holds the same binary as the archive ([OIK-170](https://linear.app/oikade/issue/OIK-170)). A milestone is a full release (`0.1.0`), and the versions between milestones are pre-releases of the next one (`0.2.0-alpha.N`). Design: [OIK-63](https://linear.app/oikade/issue/OIK-63).
