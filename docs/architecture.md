# Architecture

How Oikade works inside, as it is now. It's for anyone changing the code. What a user writes and sees is in the [README](../README.md) and the guides it lists, and the plugin protocol is in [plugin-contract.md](plugin-contract.md).

This page says how things work, not why they were chosen. Each section links the Linear issue that holds the design and its discussion. When a change makes a section wrong, the same PR fixes it.

## Who owns what

| Owner | Holds |
|---|---|
| Git, as a Go module | Your automations: decisions, flows, arbitration settings, and a copy of the device list (`oikade types`) |
| The host's data directory | Devices, names, rooms and endpoints (the registry), claims, latches, flows' journals, deployed versions, Matter's identity and fabrics, secrets |
| Apps | Their own names. Drivers find a device by its ID, never by its name in the app, and the host copies a name once ([OIK-130](https://linear.app/oikade/issue/OIK-130)) |
| Prometheus, Grafana and Loki | Values over time, changes and rule runs |

## Components

There are two binaries ([OIK-170](https://linear.app/oikade/issue/OIK-170)). `oikade-host` (`cmd/oikade-host`) is the host, and `oikade` (`cmd/oikade`) is every command you run, which reach the host over its API. `oikade` links neither `internal/host` nor Matter, and `test/cli` checks that it stays so. What both share as commands, such as reading flags and the version, is `internal/cli`. [The host](#the-host) is one process per home, with your process and each plugin as children it supervises. There's no second host, because two would run every rule twice. Anything that assumes it's highly available, or needs leader election, is a design decision.

### The data path

```
driver ──▶ hub ──▶ metrics, event log, your process, Matter bridge
  ▲
  └── Set ◀── arbitration ◀── your process, Matter bridge, oikade set
```

- **A driver** translates one integration to capabilities. It reports to a `driver.Sink` (`Discovered`, `Changed`, `Availability`, `Seen`, `Undeclared`, and `Inventory`: every device it sees in its app, declared or not) and takes writes as a `driver.Setter`. The drivers are `plugins/zigbee2mqtt`, `plugins/ewelinklan`, `plugins/overkiz`, `plugins/toshibaac` and `internal/driver/plugin`. A new kind of integration is usually a plugin.
- **The hub** (`internal/hub`) holds the latest state of each device and fans updates out.
- **Capabilities** (`internal/capability`) are the protocol-neutral names and value types every consumer uses. Drivers convert to them, and nothing after the driver knows about vendor payloads.

### Drivers

- **eWeLink LAN.** `plugins/ewelinklan` is a plugin a home imports ([OIK-10](https://linear.app/oikade/issue/OIK-10)). It joins the mDNS group through `internal/mdns`'s `ListenMulticast`, and follows `_ewelink._tcp` records, which can arrive over several packets. The TXT record's `type` picks a row of `kinds` (command path and body, capabilities, how to read a report), so another device type is another row. Reports are AES-128-CBC under the MD5 of the device's LAN key, read from a secret named for its ID, and read again whenever a report can't be decoded, so `oikade secret set` needs no deploy. Everything a report says goes through one goroutine, so what's published stays in order. Devices stay reported for the life of the process, and availability follows the age of the last relay report. A command is an encrypted POST, and `Set` returns once a newer report shows the relay moved. Its `Setup` signs in to eWeLink's cloud through the browser, keeps each device's key as a secret and keeps no token, so the plugin talks to the cloud only then.
- **Overkiz.** `plugins/overkiz` is a plugin a home imports ([OIK-17](https://linear.app/oikade/issue/OIK-17)). It speaks Overkiz's enduser API, which a TaHoma hub's local API (`Local`, a bearer token from a secret, over TLS checked against Overkiz's embedded root CA and the hub's `gateway-<pin>.local` name, read from the CN or SANs by `hubTLS` since Go ignores the CN) and Cozytouch's cloud (`Cozytouch`: Atlantic's password grant, its JWT, then an Overkiz session cookie) share. A session reads `/setup/devices` once, registers an event listener and fetches it every 5s, or every 2s while an execution runs, and reads the setup again only when a device is added or removed or the listener is forgotten. A cloud session the server ends logs in again at once, unless it ended as it began. A device's ID is `<protocol>.<address>` from its device URL, without the hub, and its sub-devices (`#2` and on) fold into it. `models` maps an Overkiz widget to a model, which reads capabilities from all of a device's and its sub-devices' states and picks its commands from them, as a towel radiator's setpoint follows its mode. Errors are classified by `errorCode` and message into unreachable (backoff), refused (wait for the secret to change, or an hour), limited and a forgotten listener, and each is the plugin's status `error`. While there's no session every device is offline and the discovered list is nil. `Set` returns once the execution is accepted. A `Cozytouch` account is also on Magellan, Atlantic's own cloud ([OIK-329](https://linear.app/oikade/issue/OIK-329)): `clouds` runs the Overkiz `bridge` and a `magellan` side together, each with its own `follower` (the login, backoff and secret loop they share), one `signer` holding Atlantic's token and any refusal for both, and a `share` that merges what each reports into the plugin's devices, discovered list (nil while either can't see its app) and problem. A cloud with no account for the login (`absent`, such as Overkiz's "No such user account") reports nothing and isn't a problem. Magellan has no events: its `setupviewv2` is read every minute, and after a write once its executions are done, and a device's numbered capabilities map to a model by `modelId` in `magellanModels`.
- **Toshiba Home AC Control.** `plugins/toshibaac` is a plugin a home imports ([OIK-256](https://linear.app/oikade/issue/OIK-256)). The units' WiFi modules only connect out, so it speaks the app's cloud protocol, as KaSroka/Toshiba-AC-control documents it, with the headers vmvelev/Toshiba-AC-control found the cloud has wanted since July 2026 ([OIK-327](https://linear.app/oikade/issue/OIK-327)): every request carries a `Device-ID`, 16 hex digits of the hash the client ID uses, as the app sends its Android ID, and no User-Agent, since a login without the one is answered 429 and a browser's User-Agent 403. Then a JSON login over HTTPS, `RegisterMobileDevice` as one client ID per account (the username and a hash of it, so the account doesn't collect devices), which gives an Azure IoT Hub SAS token, and the account's units from `GetConsumerACMapping`. It then connects to the hub named in the token's `sr` as that device, over MQTT 3.1.1 (`mqttConn`: connect, one subscription, publish at QoS 0 and 1, and keep-alive). The hub refuses MQTT 5, so paho.golang can't be used. The cloud calls the device's direct method `smmobile` with `CMD_FCU_FROM_AC`, a unit's state as hex in which a field it doesn't report is a none value, so `fcuState` updates only the fields it has, and `CMD_HEARTBEAT`, its room temperature. Each call is answered with status 0, as the app's SDK does. A write is a device-to-cloud message on `devices/<device>/messages/events/` at QoS 1, `CMD_FCU_TO_AC` with a state in which only what changes is set (`command`), written as the library writes it, Python's `str()` of a dict. `Set` returns on the hub's PUBACK, and works out a write from the unit's state with the writes sent since its last report (`intent`, recorded under the plugin's lock before the write is sent, and counting for a minute at most), so a mode and a setpoint sent together see the new mode. It refuses a setpoint that isn't whole degrees or a mode bits 6 and 7 of the unit's `MeritFeature` rule out. Units in the same list of `Config.OutdoorUnits` share an outdoor unit ([OIK-323](https://linear.app/oikade/issue/OIK-323)), which the cloud doesn't say: a write that turns one on or changes its mode is checked against the others' state with their writes, and refused if heating would run beside cooling or dry, or auto beside another mode but fan, which runs beside any ([OIK-324](https://linear.app/oikade/issue/OIK-324)) (`clashes`). Calls go through the session's goroutine, which also takes every unit's state as read over HTTP every 30 minutes, beside the hub, so a slow read doesn't hold up its calls, and a read that fails is only logged. A device's ID is the unit's `DeviceUniqueId`, in lower case. A session whose access token (a 401) or SAS token (5 minutes before its `se`, or halfway through a shorter one) runs out starts again at once with its units online, unless it ended as it began, and only a session that lasted resets the backoff. Errors are refused (wait for the secret to change, or an hour), limited (a 403 or 429: 10 minutes) and anything else (backoff), and each is the plugin's status `error`. While there's no session every unit is offline and the discovered list is nil.
- **Zigbee2MQTT.** `plugins/zigbee2mqtt` is a plugin a home imports. It maps each device's exposes to capabilities. It connects to a Zigbee2MQTT and a broker you run, and the host starts neither ([OIK-155](https://linear.app/oikade/issue/OIK-155)). It reports every paired device by IEEE address, with `ReportState`. After each device list it sends a paced `/get` for each property that an expose's `access` says can be read and that has no value yet, retained or reported, on a device Zigbee2MQTT doesn't say is offline ([OIK-53](https://linear.app/oikade/issue/OIK-53)). A sleeping sensor can't be asked, so it relies on `retain`. It treats `<base>/bridge/state`, which is Zigbee2MQTT's Last Will, and its own broker connection as the health of Zigbee2MQTT: either going offline marks its devices offline and refuses writes.
- **Plugins** speak the [oikade/v1 contract](plugin-contract.md) under `oikade/v1/<plugin>/`. The driver validates every message against the contract and the capability registry, and drops and counts what doesn't fit. The Go SDK is `sdk/plugin`, and the contract types are `contract/v1`. First-party plugins live in `plugins/`, and anyone else's in its own repo, which checks itself with the `oikade-conformance` command (`cmd/oikade-conformance`, wrapping `internal/conformance`), as [plugin-contract.md](plugin-contract.md#conformance) describes. Here, `make test-conformance` drives the simulated-relay fixture `test/fixtures/simswitch` through it, so an SDK change is tested end to end in its own PR. Design: [OIK-61](https://linear.app/oikade/issue/OIK-61) (plugin drivers) and [OIK-62](https://linear.app/oikade/issue/OIK-62) (the Go SDK).

## The host

`oikade-host` (`cmd/oikade-host`, `internal/host`) is how Oikade runs ([OIK-143](https://linear.app/oikade/issue/OIK-143)). `oikade-host install` (`internal/install`) puts it under systemd, or upgrades it, on the machine itself: its steps take a root directory, a command runner and the socket as a function, so its tests run with a fake `systemctl` ([OIK-277](https://linear.app/oikade/issue/OIK-277)).

```
                 host (long-lived)                         your process (replaceable)
┌──────────────────────────────────────────┐          ┌───────────────────────────────┐
│ device state (hub.Store)                 │─changes─▶│ mirror of device state        │
│ arbitration (an engine with no rules)    │◀─claims──│ triggers, conditions, holds   │
│ device writes                            │◀─writes──│ (an engine with no arbiters)  │
│ the store: hold state, latches, claims,  │◀─saves───│                               │
│ the journal                              │─ping────▶│                               │
│ supervision, your binaries               │◀─pong────│                               │
│ the Matter bridge                        │          │                               │
└──────────────────────────────────────────┘          └───────────────────────────────┘
```

- **The split.** Both sides run the real `internal/engine`. The host's has no rules, so it only runs arbiters and their timers, and owns the store. Yours has every rule and no arbiters: `engine.Arbitration` sends its claims to the host, `engine.States` saves hold state there, and writes go through `driver.Setter`.
- **Your process** is your binary, built from `oikade`, the public package at the module root. A home's `main` adds decisions, flows and plugins to an `oikade.Home` and calls its `Run`. Its exported API can't mention `internal/`: `internal/apicheck` fails a test if it does.
- **The mirror.** Conditions read a copy of the device state held in your process, so they never wait for a socket. So do hold states, read once from the `welcome`: the engine reads them with its lock held. Everything that changes the host's state is a request that waits for its answer, and none is sent with the lock held.
- **Surviving a kill.** Device state, claims and latches are in the host, so killing your process loses none of them. The next process gets the saved hold states and works each hold out again, and writes only if the hold started or ended meanwhile. A write and its save aren't atomic, so each goes in the order a kill between them can repair. A start's claim outlives your process, so the hold is saved as active before it claims (`Engine.saveStart`, when every device it reaches is arbitrated), and a process killed in between loads it active and claims again, latch and all, rather than inactive with nothing to end the claim ([OIK-299](https://linear.app/oikade/issue/OIK-299)). A plain write ends with your process, so it's saved after, and a process killed in between writes the start again if it's still due. An end releases or writes first and saves after, so a kill in between ends the hold again.
- **Supervision.** The host starts your process, restarts it with backoff, and kills one that stops answering. A condition stuck in a loop stops the answers. Exactly one process runs at a time, and the host refuses any other. [host-protocol.md](host-protocol.md) has the details, and says what happens to a process's claims.
- **Claims outlive a crash of the host.** Saving arbiters' state is a background job. The host's answer to a claim or a release is a promise, so it saves first (`Engine.flushControls`). An arbiter's other changes, such as a write it has made, still save in the background.
- **Durable flows** (`internal/flow`). A flow is ordinary Go, and [writing-flows.md](writing-flows.md) is how to write one. Each step sends a journal entry, the host writes it to the store, and only then does the flow continue. A step's effect comes first and its entry second, so a crash between the two repeats the effect: actions run at least once. After a crash the `welcome` returns every unfinished run, and the flow reruns from the top with recorded steps returning their recorded results. The first step that isn't recorded is where it carries on.
- **What can't resume.** An entry records a step's kind and arguments, so a replay notices code that takes different steps, and drops the run and logs it. A run past its latest useful time gives up, and logs that, unless it's a Safety flow. A run's ID is never reused, since the journal numbers a run from 1. Only the newest run of a flow resumes, and `internal/flow` stops a run by panicking through the flow, because a step has no error to return for these.
- **Times of day.** Sunrise and sunset are worked out in your process by `internal/sun`, for the location in the home's `oikade.Options`, which `oikade` gives `Engine.Site`. `simhome` takes the same `Site`, so `oikade dev`, `oikade replay` and `hometest` agree with the house. The host's engine only arbitrates, and has none. `Compiled.Since` comes from the host, which saves when each rule's timers were last accounted for. So a time missed while no process ran fires when one starts, within the same limit as a late flow, and a save lost to a crash means catching up once more.
- **Stopping** (`internal/host/shutdown.go`). `Host.Run` keeps each part in a `stage` with its own context, so a part ends when its phase comes and not when the signal does: API, automations, writes under way, plugins, Matter, then the engine and the store. The engine goes late because a controller's write goes through it. A write counts as under way until the driver has it (`routedSetter`), while the engine has work in flight (`Engine.Idle`), and, for a controller's, until its burst has been sent (`Coalescer.Busy`). That wait has a limit of its own, so a stuck write can't take the plugins' turn. The contract has no acknowledgement of a `/set`, so what a plugin does with one it's been given is up to the plugin as it handles `SIGTERM`. `--stop-timeout` bounds the whole order. A phase still running at the deadline is left behind, the processes still running are killed, the host exits with an error, and the store isn't closed, as closing would wait for it. That's safe because every write is on disk before anything depends on it. Only events still queued for the event log are lost. A plugin's socket ends by itself once its process has gone, so everything it said before going gets read. The Matter node sends CloseSession on each session, within a second, before its socket and mDNS responder close, so a controller learns at once and not at its own timeout ([OIK-217](https://linear.app/oikade/issue/OIK-217)).

- **Deploys.** The host keeps your binaries in the data directory, and the store says which is running. `oikade deploy` checks your flows and builds your module for the host's platform, and the host checks the result before anything stops. It stops the old process, starts the new one and watches it settle, and a failure brings the last one back. [host-protocol.md](host-protocol.md#deploys) has the order. `--home` only says what to run until the first deploy.
- **The API** (`internal/host/api`, [`docs/host-api.md`](host-api.md)). HTTP on `api.sock`, one connection a call, with newline-delimited JSON for `tail`, which `internal/host/feed.go` fans out without ever waiting for a reader. It's apart from `host.sock`, which only your process uses, and both are `0600`. A `Transport` reaches it: `Local` dials the socket, which needs no authentication of its own, and `Remote` dials the network API with a pinned key and a token. `--api-addr` serves the same routes over TLS (`internal/host/apiauth.go`), with a self-signed key in the store's `api` namespace and a bearer token for each client, kept as its SHA-256.
- **The device registry** (`internal/registry`). The store holds it as one value, so a device and the endpoint counter can't disagree after a crash, and an unreadable one stops the host rather than starting empty and handing out endpoints again. `internal/host/devices.go` keeps the live state in `hub.Store` in step, by giving each driver instance the registry's devices: the hub's key is the registry's name, and a driver finds that from its hardware's ID. An endpoint belongs to one registry entry for good: `Next` only rises, removed devices stay on record, and a name moved onto new hardware keeps its entry's endpoint and retires the replacement's. Claims are keyed by name, so a declared rename moves them (`Engine.MoveDevices`, before the hub renames, with the old name given no arbiters meanwhile, and its own cases' claims, holds, fires, pauses and averages moved to the new name's keys, which are only those the new version's Control has on the device (`wire.OwnCases`), since a group's cases can be keyed by a name a device has too; a failure puts everything back), and removing a device ends its claims (`Engine.ForgetDevice`) rather than leaving them for the next device of that name. Claims a device has only on disk count too (`Engine.SavedClaims`). A record that can't be read counts as a Safety claim on the whole device (`Engine.UnreadableClaim`): it stays, no arbiter starts empty to save over it, `claimedSetter` refuses every write to the device, and removing the device with `--allow-safety` clears it. A device's arbitration settings are on record with it, so a host loads its arbiters as soon as a driver instance attaches, and a claim holds before the device reports. A home's `Control` arrives in the process's Hello, and overlays them by capability. It's saved first, in its own namespace, so a host that restarts arbitrates what the last code said before any process attaches. A process only adds and changes settings (`inventory.takeHome`), and a process turned away has no say. Dropping one ends its claims, so that waits for the version to settle (`deployer.removals`), and a deploy that would end a Safety claim that way is refused without `--allow-safety-removal`. A deploy also refuses declarations that take a device out of a Safety case's room write, by its room or type (`inventory.leavingSafety`), comparing each case with the same one in the old version. `oikade types` renders the registry to Go (`internal/registry/types.go`), as the home's declarations would make it (`registry.Declaring`, on the manifest of the home it builds, or on the declarations in its source when it doesn't build, as it doesn't when it names a handle only the new file has): a value per device, with its name and an `oikade.Bool`, `oikade.Number` or `oikade.Choice` for each capability it has, named by the capability registry's `Go` name, so the compiler checks what a home names. Nothing else is in the file: `oikade dev` and `hometest` read the handles back from its Go (`registry.Handles`), with rooms and types from the home's declarations. Your process isn't told a device went: it's told about new and changed ones, and a deploy gives it a fresh list. A device stays until you remove it.
- **Plugins** (`internal/host/plugins.go`). Each plugin your binary imports runs as `<binary> plugin <name>`, with the same supervision and heartbeat as your automations (`Host.watch`) and its own backoff. The host learns their names from check mode, and only a change of binary restarts them, so a deploy does and a crash of your automations doesn't. The SDK's `Plugin` publishes through a `link`, a broker or the host's socket, so a `Handler` is the same on both. A plugin process speaks `internal/host/pluginwire`, the part of the protocol with no engine types, so the SDK doesn't link the engine. `socketBus` makes a session look like an `mqtt.Bus`, so `internal/driver/plugin` decodes imported and outside plugins alike, and there's one set of checks. A plugin outlives its processes in the host: its decoder stays, and it keeps a process's devices known while none runs. Every plugin on record attaches at start, so a claim on its devices is enforced before any process connects, and `routedSetter` sends each write to the device's driver, for your code, `oikade set` and Matter alike. After a `devices` report the host records what it hears in the registry, and tells the decoder which device each ID is, which is why a plugin needs no list of devices. `Engine.RuleClaims` and `EndRule` also see claims that are only on disk, for a device whose driver is yet to attach, so a deploy check can't miss one.
- **Matter** (`internal/host/matter.go`). The node runs in the host with no bus between them, so controllers don't notice your process. `matterBridge` wraps `matterbridge.Bridge`, which is a `driver.Sink` of the hub, and calls its `Apply` with what the registry says whenever the registry or a device's discovery changes. A bridged device's `UniqueID` comes from the bridge's unique ID and the endpoint, because the endpoint is what follows a device through a rename or a replacement. Only reserved and removed devices stay off, and those of plugins the home hides from Matter, which keep their endpoints. Which plugins those are, and the bridge's name, come in the automations process's Hello, and `homeOptions` saves them in the store's `options` namespace before they're applied, so a restart applies the last deploy's before a process connects. While a deploy is settling, its Hello's hidden plugins are ignored, and `deployer.hide` takes them from the manifest once it's confirmed, so a version that fails costs controllers nothing. `api.Bridgeable` (paired, with a device type) is what the bridge, `oikade devices` and a deploy's `takenOffMatter` count as on the bridge, and a test keeps it equal to `matterbridge.Supported`. The store's `matter` namespace holds the `identity`, written once before a controller can see it, and the `fabrics`. `fabric.Table` saves through `fabric.Store`, so a fabric is on disk before commissioning hears it worked. Unreadable Matter state leaves the bridge broken for good, with no node and nothing retried, and the home running: a new identity would lose every controller silently, and `oikade matter` and the log say why. A bridge that can't start or stops serving, as with a taken port, tries again every `matterRetry`, and `node.Run` can run again after it returns. A Window Covering logs each command a controller sends, with its target, as `Took Matter command`, so the log says what was asked as well as what was written ([OIK-337](https://linear.app/oikade/issue/OIK-337)). A controller's write goes through `matterWrites`: it refuses against a Safety claim, on disk or in an arbiter, then records the write, so the device's change counts as `Matter`. A report that differs from the arbiter's last write is ignored while the write settles, for `capability.SettleOf`: the capability's `Spec.Settle`, 2 min for `position` and 30 s for `locked`, or `DefaultSettle`, 5 s. The device's value is looked at again once it's up, so a blind's travel isn't an outside change and one that stopped partway is. A write from Matter or `oikade set` settles the same way, except that the report it's waiting for counts at once, and it matches the device's change for 25 s after it has settled.
- **Pauses.** The store holds them, and the host tells your process in the `welcome`, then with `pause` and `resume` messages. The process keeps a paused rule out of its engine. The host ends the rule's claims as well, since no process may be running to do it.
- **Metrics.** Host and device metrics come from the host. Rules run in your process, which sends its metrics in Prometheus's text format every 5 seconds, so Prometheus scrapes one target that outlives deploys. `internal/host/observe.go` merges them. The Matter bridge's come from an `im.Observer` the node hands to its Interaction Model server, and from the node's fabrics, sessions and subscriptions, read at each scrape (`internal/host/matter_metrics.go`). Their labels are a cluster's name and a status, never a node ID, which a controller chooses. The HTTP listener only reads.
- **Fault points.** `internal/fault` marks where a crash matters, and compiles to nothing unless built with the `faultpoints` tag, which only `test/host` uses. `TestKilledAtEveryJournalBoundary` uses them to kill each side at every journal write, just before and just after it's durable. `TestBrokenWriteAheadFailsTheCheck` proves that test can fail. The registry, the home's options, the Matter fabric table, secrets and a deploy's upload each have a point between their write reaching disk and its answer, and `test/host/faults_test.go` kills the host there and starts it again, to show that what it was told survives. A hold's start has one after its claim (`client.hold.started`), where a test holds your process, lets the hold's condition pass and kills it. A test can plan a fault once the host is running: a host reads the plan at its first hit after the file appears.
- **Secrets** (`internal/host/secrets.go`). A directory with one file each. The host passes on the directory as `OIKADE_SECRETS_DIR`, never a value, so nothing reads one but the code it's for. `oikade secret set` is the one call that carries a value, and it's in no log or answer. A read-only directory means they're managed elsewhere. `mqtt.Connect` doesn't quote its URL in errors, and the host's logs use `redacted`, since a URL can carry a password.

## Rules

The engine (`internal/engine`) runs what `oikade` compiles from your home, in your process. Design: [OIK-64](https://linear.app/oikade/issue/OIK-64) (the rule model) and [OIK-60](https://linear.app/oikade/issue/OIK-60) (room targets).

- **Flows** start when a trigger fires and the condition holds, and run in `internal/flow`, which journals each step in the host. Times of day are timers. A room target resolves to its members when the trigger or `Set` runs, not when the rule loads, so a device added to a room is covered at once. A flow's `Set` ranks at its own `Flows(f)` line in the decision, `Rule/<flow>` in the entry's `lines`, or else at `flows` (`claimPriority`), and a flow any decision ranks above its override line is Safety (`flowSafety`). A flow's `Set` on a room of device types leaves the other types out as written, and logs them once, but a member it leaves out because it arbitrates the capability, with no `For` or `Until`, is the step's error.
- **Decisions** ([OIK-298](https://linear.app/oikade/issue/OIK-298)) compile in `oikade` (`decide.go`) to the host's `control.Entry` for the capability, and an engine hold for each case and budget line, keyed `<device> <capability> <case>`. A case above the override line, or every case with `NoOverride`, is a Safety hold. A case's `LatchUntil` is the hold's `Until`, which ends its latch. A budget line's conditions are its hold's `When`. A `Follow` line is a hold with `Follow`, which works out its value on every look: it's active while the reading is known, rounds to `Step` or the capability's `Spec.Step`, and claims again only when the value is three quarters of a step from `HoldState.Target`, the last one written, which the host saves.
- **Holds** aren't timed in memory. The engine works out from the clock and the devices' state whether each hold is active, and when that next changes. It saves each hold's state, so after a restart it writes only if the hold started or ended while it was down. An inactive hold's `WhyNot` says why, which your process sends the host as a `whyNot` message for `oikade status`.
- **Rolling averages** (`internal/engine/average.go`) are the `engine.Average`s that `AverageOver` made as the home was built, which `oikade` gives `Engine.Averages`. Each takes every report of its reading into time-weighted buckets, a window's 48th each, and is saved in the host's `averages` namespace through `saveAverage` when a report lands in a new bucket, and every changed one when the engine stops. A condition reads one as a capability of its device, `temperature over 24h`, which the engine adds to the devices it looks at, and a budget's `Bands` read it the same way.
- **A report is applied as a whole** ([OIK-212](https://linear.app/oikade/issue/OIK-212)). A driver passes every value one report from a device changed to `driver.Sink.Changed` in one call, the store takes them all in before its listeners hear, the host sends them to your process as one `change`, and the engine handles them as one event. So every hold looks at the whole report. The writes the holds start in one look, a report or a timer, then run in order (`Engine.startWrites`). Claims that start go before claims that end, so a line that takes over from another at the same moment has claimed before the other lets go, and the arbiter never falls back to the default on the way ([OIK-343](https://linear.app/oikade/issue/OIK-343)). Then they go highest level first: a Safety claim is in before a Normal one from the same report, so the arbiter never writes the Normal value, even for a moment. Plain writes, with no `Control` to arbitrate them, go the other way: ends first, since a bool hold's end writes the opposite of its value, then lowest level first, so a start's value, and the highest level's, is the one that stays. Only writes that can reach the same device, in one room or to one device with no room, wait for each other, and a write to a group's members joins the rooms they're in. A flow the same look sets off starts once those writes are in. `oikade replay` puts a device's changes at the same moment back into one report.
- **Arbitration** (`internal/control`) decides an arbitrated capability. Rules, Matter controllers and the device itself make claims at a level (Safety, Override, Normal). The highest level wins. Within a level, the entry's `lines` rank claims, highest first: each is a rule's source, `override` for an outside change or `flows` for any rule not named, and the later claim wins a tie. Then the equipment limits hold the winner back. A controller's write reaches the engine in the host, so it becomes a `Matter` claim. The engine and the store keep a claim's source as `Rule/<key>`, `Matter`, `Device` or `Command`, and a rule's key as `<device> <capability> <case>` or a flow's name, so saved claims, pauses and lines don't move. The host API and `internal/simhome` give it as its ref (`control.SourceRef`, `control.RuleKey` back), the grammar of which is `internal/ident`'s `ParseRef`. An arbiter that starts from a saved state, as after the host starts, takes the device's first report as what the device is now, and never as an outside change, as it does when a driver gets a new process and a write may not have been made (`Engine.DriverReturned`). So whether a report or a deploy's removals come first at startup doesn't decide an Override ([OIK-318](https://linear.app/oikade/issue/OIK-318)), and the arbiter writes the winner again if the device disagrees.
- **Rules in Go** (`internal/engine/rule.go`). `NewHold`, `NewFlow` and `NewTrigger` build the engine's input, which `oikade` calls for [the host](#the-host). A condition runs with the engine's lock held, so it must not block. Its `Vars` carry each device's values and its room and device types (`hub.Member`), so a condition can read a room ([OIK-180](https://linear.app/oikade/issue/OIK-180)). A hold with a condition looks again on any change to a device, and when a device is announced again, as a move to another room or a new device type announces it. A hold writes a device, a group's members (`Devices`) or a room's devices, apart from those with a decision of their own (`Except`). A group's or a room's start writes the members it can, and is active once it has reached one: a member that isn't discovered yet, or whose write failed, gets the start once it's discovered or at its retry (`Engine.joined`). That retry doesn't hold up the hold's end, and a group's end writes back only the members it wrote ([OIK-321](https://linear.app/oikade/issue/OIK-321)). After a restart, an active hold counts every member as written, so one whose write was still to retry isn't written until the hold starts again. A group's decision compiles to one hold per case over its members, and to a setting for each member, with a member's own lines ahead of the group's when it hands over with `Then`. A room's decision is one setting for the room (`wire.DeviceControl.Room`), which the host gives each device there of its types with the capability and no setting of its own (`wire.SettingsFor`), so a move needs no deploy.
- **Conditions** are values in `oikade` (`condition.go`), each of which can say whether it holds, why it doesn't, and what's wrong with it for `oikade check` ([OIK-298](https://linear.app/oikade/issue/OIK-298)). `toEngine` makes one an `engine.Condition`. A hold's `Daily`, alone or in an `All`, becomes the engine's `Window` (`splitHours`), so it starts and ends on its edge. A flow's `Get` and `Is` are `look` steps in its journal, read through `Engine.Look`, so a replay returns what the run first read. A `Becomes` is an `engine.Change` with `To`, which fires only on a change to that value.
- **The day planner** (`internal/schedule`) lays out a day in 15-minute slots that rules require, forbid or prefer, and spends a daily budget across them. A budget is a `schedule.Spec`, and its plan lives in `HoldState.Budget`, so it survives a deploy.

### Simulated homes

`internal/simhome` runs a home in one process: one `Engine` with both rules and arbiters on a fake clock, with its states and journal in memory. `oikade dev` is your binary's `dev` role reading commands from standard input, and `hometest` is the same thing in a test. `oikade` fills in `simhome.FromHome` when it loads, because a public package can't name a home's compiled form. `Sim.settle` needs to know the engine has caught up, and `Engine.Idle` says so exactly: the engine counts what it has in flight (changes queued, a wake or save asked for, every goroutine it starts), and a run stops counting while it waits through `Engine.Park`, as the engine's own waits and a flow's do. A parked run whose time has come, or whose change has happened, isn't waiting any more, a run cancelled mid-wait is busy until it ends, a failed save is owed until one succeeds, and the engine knows when its own timer is due. `settle` doesn't poll `Idle`: it checks again when `Engine.MaybeIdle` says the count has fallen to zero or the timer was set, because on Linux a sleep shorter than a millisecond takes one, and polling made a test of a simulated day take 40 seconds ([OIK-314](https://linear.app/oikade/issue/OIK-314)). `Engine.ParkedUntil` says when the next parked run wakes, so `Advance` can move straight to the next wake-up. A restart builds a new engine from the states and journal, as a new process would, so `flow.Recover` runs for real.

`oikade replay` is a `Sim` too (`internal/simhome/replay.go`). The command builds your module and hands its binary a file with the host's event log, and the binary runs the log through a `Sim` and prints a report, so the host never runs your working copy. Changes within 10 seconds of a write to the same capability are the device answering it, and don't go in: otherwise the deployed version's writes would happen whatever your code does. A device's first value starts it off, rather than going in as a change. If the log begins with the deployed version's process connecting, your code starts when it did, with what the devices said before that as how they were, and what each wrote on starting is compared. Otherwise your code starts a second before the first event, and neither's writes on starting count ([OIK-320](https://linear.app/oikade/issue/OIK-320)). Flows' outside calls don't run: `Flow.Dry` answers each from the log, by name and in order.

### Embedded store

`internal/store` is [the host's](#the-host) state store.

- One data directory holds one [bbolt](https://github.com/etcd-io/bbolt) file, `oikade.db`, and only one process can have it open. The operating system drops that lock when the process dies, so a crash never leaves it locked. A second process gets a clear error.
- Namespaces share the file with separate keys, for the registry, latches, claims and Matter state, its saved subscriptions among them. `engine.Stored` implements `engine.States` on a namespace.
- The journal keeps ordered entries per run. `Append` returns only once its entry is on disk. Each write is one transaction with two fsyncs, so its cost is about twice the disk's fsync time. A crash mid-write loses only the entry that was never acknowledged.
- The file records its format version, and `Open` refuses one it doesn't know. It also refuses, with the same `ErrFormat`, a file that isn't bbolt's, or one shorter than its meta page says, which it checks before bbolt maps it, because bbolt reading past the end of a file cut short faults the process ([OIK-307](https://linear.app/oikade/issue/OIK-307)).

The event log (`store.Events`, fed by `internal/host/eventlog.go`) lives here too, as what `oikade replay` reads. It's history, not state: nothing depends on it, so it trades the rest of the store's durability for staying out of the way. Reporting an event only appends to a queue. One commit every 5 seconds takes the queue, so a crash loses at most that long, and past 4096 waiting events new ones are dropped, not waited for. With nothing queued and nothing over the bound there's no commit, so an idle host doesn't sync the disk. That commit also drops the oldest events over the bound, folding their last values into a baseline in the same transaction, because a device that hasn't changed since still has them. A reader takes the log in pages, each its own short transaction: a long one would hold up writes that grow the file, journal entries among them.

The default bound is 14 days or 64 MiB, whichever comes first. It's sized on an estimated home of 50 devices at about 24,000 events a day, which holds 14 days in about 31 MiB and a 48 MiB file, so the size bound has room for a home twice as busy. That estimate is in `internal/host/eventlog_test.go`, and no real home has measured it yet. With a full 64 MiB log and a commit every 20 ms, the journal's median append went from 9.0 to 10.0 ms on a Mac's SSD, measured once by hand. Timings vary too much to test, so `TestAFullLogDoesntSlowTheJournal` checks what they allocate instead: a log commit at most a page more in a log four times the size, and a journal append at most a page more with a full log than with none.

## Matter

Oikade reaches the Home app and other controllers as a Matter bridge. It replaced a HomeKit bridge built on an unmaintained library ([OIK-76](https://linear.app/oikade/issue/OIK-76)). The Matter stack is Oikade's own, in `internal/matter`, built from the Matter Core Specification: TLV, the message layer with MRP over UDP, PASE and CASE, operational certificates, the Interaction Model, the commissioning clusters, attestation with connectedhomeip's test DAC, and an mDNS responder, which also finds a node by operational discovery: a one-shot lookup of its `_matter._tcp` instance on the responder's own sockets ([OIK-209](https://linear.app/oikade/issue/OIK-209)). `internal/matter/node` wires them into a node serving a bridge, and [the host](#the-host) runs one. Primitives, certificates and setup payloads are checked against published vectors, and PASE, CASE with its resumption and the encrypted message against handshakes recorded with chip-tool, which connectedhomeip's own tests don't pin (`internal/matter/securechannel/testdata`, [OIK-306](https://linear.app/oikade/issue/OIK-306)).

- **The mapping** (`internal/matterbridge`) makes each device on record with an endpoint ID one bridged endpoint, with a device type per function and their clusters, and Power Source for a battery. What a device that's on or off is comes from `internal/devicetype`, the one answer `oikade devices` reads too: the registry's `deviceType`, which a declaration's `Is` sets, else its `driverDeviceType`, from the driver's report, else a dimmable light with `brightness` and a plug-in unit without ([OIK-142](https://linear.app/oikade/issue/OIK-142)). Level Control comes with a dimmable type, not with `brightness` alone. A device with a `setpoint` is a Thermostat with only the Heating feature instead, whose Thermostat cluster carries its `on` and `temperature` too ([OIK-20](https://linear.app/oikade/issue/OIK-20)). One with a `mode` and an `on` as well is a Room Air Conditioner (`devicetype.ClimateOf`): a Thermostat with Heating, Cooling and Auto and a dead band of 0, so both occupied setpoints are its `setpoint`, and an On/Off. Its SystemMode is `on` and `mode` together, so a controller's one write can be two, which the `Coalescer` sends mode first, as it sends any value before an on and after an off ([OIK-263](https://linear.app/oikade/issue/OIK-263)). A Door Lock's LockState follows the lock's reports and never its commands, so a controller can't show a bolt that hasn't moved, and a Window Covering's Current position does the same, while its Target comes from the command. A move shows as moving until a report reaches the target or `position`'s settle has passed on the bridge's clock, and a write that's refused cancels it (`Mapped.Cancel`) ([OIK-23](https://linear.app/oikade/issue/OIK-23)). A device whose capabilities or device type change is rebuilt on the same endpoint ID. A new name isn't a rebuild: it sets the Bridged Device Basic Information's NodeLabel in place, and subscribers are sent it ([OIK-130](https://linear.app/oikade/issue/OIK-130)). State reaches attributes under the node's lock, and availability is the Bridged Device Basic Information's Reachable.
- **Writes** from controllers go through a coalescer: per device and capability the last command in a 50 ms window wins, and one that matches the device's state is dropped. A device's bursts are sent one at a time, in order, so a slow device can't take an older command after a newer one.
- **Commissioning** (`internal/matter/clusters`) owns every commissioning window, including the initial one the node opens while it's on no fabric, which closes after 15 minutes, on RevokeCommissioning, or once commissioned. `oikade matter open` reaches `node.OpenWindow` through the host API: the initial window again while the node is on no fabric, and once it's on one, an enhanced window with a passcode, salt and discriminator made for it. It replaces only a window the node or its owner opened, never a controller's, and waits for the commissioning hooks, so PASE takes the new verifier before it answers. `internal/qr` draws the QR code: alphanumeric mode, level M, versions 1 to 6, as a Matter payload needs no more. The node advertises each fabric's operational service when AddNOC or UpdateNOC changes it, and again when the fail-safe rolls it back. Ending a session sends CloseSession, and a peer's CloseSession ends its session.
- **Subscriptions** (`internal/matter/im`) report a change at most every min interval, the subscriber's floor, and send an empty report when nothing has changed for the max interval. The bridge grants a max of 60 s, or the subscriber's ceiling if that's shorter, but never below its floor, which the spec's bounds for a publisher allow (Core spec 8.5: from the floor to max(60 min, ceiling)). Apple's home hub asks for 10 minutes, and was seen to ignore CloseSession and subscribe again only once a report was late, so this bounds how long it takes to come back after a restart: about max(floor, 60 s), plus some seconds ([OIK-209](https://linear.app/oikade/issue/OIK-209)). Each subscription over CASE is saved in the store after its Subscribe Response, with the subscriber's node ID, paths, intervals and last address, never keys (`internal/host/matter_subscriptions.go`). Its record goes when the client replaces it, refuses a report with INVALID_SUBSCRIPTION, or its fabric is removed, and when another subscription is saved after it has ended. It stays when the host stops, which is what it's for. At each start the node resumes them: for each record it finds the subscriber by operational discovery, else at its last address, opens CASE to it as the initiator, and sends a priming report under the old subscription ID, then runs it as if just subscribed (`internal/matter/node/resume.go`), as the reference SDK, matter.js and rs-matter do. It tries again after 1, 2, 4… seconds, and gives up and deletes the record once the next wait would pass one max interval, by when the subscriber has noticed and will subscribe again itself, or at once if it refuses. A new subscription ID is never one that's saved, and a client that subscribes afresh before its old one is resumed replaces that one too.
- **Panics** (`internal/matter/contain`). Matter parses whatever anyone on the network sends, so a bug there costs the message and its session, not the home ([OIK-172](https://linear.app/oikade/issue/OIK-172)). It's the one place the host recovers from a panic, and only for work whose state goes with it: the transport's read of each packet, each handler on its exchange, each subscription's reports, and the mDNS responder's answer to a packet. Each defers `contain.Recover` itself, since a recover covers only its own goroutine. A panic ends the session it came on as the node always does, with CloseSession on a secure one, so the controller starts again, and a handshake that panics takes out the secure session it had added. The locks those paths take go with `defer`, the Node's included, and what an Update changed before a panic is still announced, so a contained panic can't leave a lock held and turn a crash into a hang. Some state can't be left half moved: the commissioning clusters' commands and writes defer `contain.Critical`, which `Recover` passes on, and timers and commissioning hooks aren't contained, so a panic there stops the host, which starts again clean. Each contained panic is logged with its stack and counted through the node's `im.Observer` in `oikade_matter_panics_total`.

## Releases

release-please keeps a release PR open on main. Merging it tags the release, and `.github/workflows/release.yml` runs GoReleaser (`.goreleaser.yaml`) on the tag: it builds `oikade` for darwin and linux and `oikade-host` for linux, on arm64 and amd64, attaches them as `.tar.gz` archives with checksums to the Release release-please made, keeping its notes, and pushes the image. The Dockerfile copies the prebuilt `oikade-host` rather than compiling it, so the image holds the same binary as the archive ([OIK-170](https://linear.app/oikade/issue/OIK-170)). A milestone is a full release (`0.1.0`), and the versions between milestones are pre-releases of the next one (`0.2.0-alpha.N`). Design: [OIK-63](https://linear.app/oikade/issue/OIK-63). Everything is built with cgo off, so it's static and runs on distroless. On Linux, that means Go's own resolver, which never does mDNS, so wherever Oikade dials an address you give it (an Overkiz hub, an MQTT broker, `oikade`'s host), it dials through `internal/mdns`'s `DialContext`, which looks a `.local` name up over mDNS, and with the system's resolver only if nothing answers there, since a router's DNS may answer for any name. That package is mDNS's sockets and nothing of Matter, so `oikade` links it too; the Matter responder, `internal/matter/mdns`, is built on it ([OIK-328](https://linear.app/oikade/issue/OIK-328)).
